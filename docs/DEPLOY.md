# Deploying Trailmark

The backend and its database go on Render, the frontend on Vercel. This needs your own accounts, so it is a checklist and not a script. Nothing has been deployed with it yet, so these steps are untested.

## Variables

| Variable | Where | Meaning |
| --- | --- | --- |
| `LLM_API_KEY` | Render | Gemini key from Google AI Studio. Empty means no AI (saved or basic mode) |
| `FRONTEND_ORIGIN` | Render | The exact frontend address, for example `https://trailmark.vercel.app`. No trailing slash, no path. Several addresses can be given separated by commas. The backend allows only these origins (and `localhost`) |
| `JWT_SECRET` | Render | Generated by `render.yaml`. The server refuses to start if `COOKIE_SECURE=true` and it is shorter than 32 characters |
| `COOKIE_SECURE`, `COOKIE_SAMESITE` | Render | `true` and `none`, set in `render.yaml`, needed when the browser calls Render directly |
| `NEXT_PUBLIC_API_URL` | Vercel | Backend address the browser calls (no trailing slash), or `same-origin` for relative paths. Not set means `http://localhost:8000` |
| `BACKEND_URL` | Vercel | Backend address that Next.js forwards to in same-origin mode. Not set means no forwarding |

`NEXT_PUBLIC_API_URL` and `BACKEND_URL` are read when the frontend is built. After changing either one, redeploy the frontend.

## Order

1. Backend on Render.
2. Frontend on Vercel.
3. Put the Vercel address into `FRONTEND_ORIGIN` on Render and redeploy the backend.

## 1. Backend and database on Render

1. Push the repository to GitHub.
2. In Render choose **New, Blueprint**, pick the repository. Render reads `render.yaml` and creates `trailmark-backend` (Docker) and `trailmark-db` (PostgreSQL).
3. It asks for the values marked `sync: false`: `LLM_API_KEY` and `FRONTEND_ORIGIN`. Enter a placeholder for `FRONTEND_ORIGIN` now and set the real value in step 3.
4. When the deploy is green, open `https://<your-service>.onrender.com/health`. It must answer `{"status": "ok"}`. `https://<your-service>.onrender.com/docs` lists every endpoint.

Free Render services sleep after a while without traffic, so the first request after a pause is slow. Open `/health` a few minutes before a demo.

## 2. Frontend on Vercel

1. Import the same repository and set the **Root Directory** to `frontend`.
2. Choose a mode:
   - **Cross-domain cookie (default).** Set `NEXT_PUBLIC_API_URL` to the Render address. The browser calls Render directly.
   - **Same-origin.** Set `BACKEND_URL` to the Render address and `NEXT_PUBLIC_API_URL` to `same-origin`. The browser talks only to the Vercel address, and Vercel forwards `/auth`, `/handovers`, `/questions`, `/statements`, `/pieces` and `/health` to Render (`rewrites` in `frontend/next.config.mjs`). The login cookie then belongs to the Vercel domain.
3. Deploy and copy the Vercel address.

## 3. Allow the frontend on Render

Set `FRONTEND_ORIGIN` on Render to the Vercel address and redeploy the backend. In same-origin mode the browser does not call Render directly, so this value matters less, but set it anyway.

## 4. Check it end to end

1. Open `<render address>/health`. It must answer `{"status": "ok"}`. In same-origin mode also open `<vercel address>/health`, which goes through the forwarding and must give the same answer.
2. Open the Vercel address in a normal browser window and pick a role.
3. Sign in works and a refresh keeps you signed in (the login cookie is set).
4. As the lead: connect the files from `data/synthetic/`, run the analysis, check the notice says `ai` or `saved`.
5. As the departing member: answer a question. As the lead: approve. As the incoming member: open the handover and confirm receipt.

## If sign-in returns 200 but the next request returns 401

The browser did not keep or send the login cookie. Check in this order:

1. Try a normal Chrome window. Strict tracking protection, private windows and Safari block cookies set by another domain.
2. Check `FRONTEND_ORIGIN` on Render. It must equal the address in the browser's address bar exactly (`https`, no trailing slash). If it does not, the browser usually shows a CORS error in the console instead. Fix it and redeploy the backend.
3. Check `COOKIE_SECURE=true` and `COOKIE_SAMESITE=none` on Render. A cross-domain cookie needs both, and the site must be on `https`.
4. If the browser still drops the cookie, switch to same-origin mode: set `BACKEND_URL` to the Render address and `NEXT_PUBLIC_API_URL` to `same-origin` on Vercel, then redeploy the frontend (both are read at build time).
5. Or put the frontend and backend under one domain, for example a custom domain with `app.` and `api.` sub-domains, and keep `COOKIE_SAMESITE=none`.

## Same-origin mode, what was tested

Tested locally: with `BACKEND_URL=http://localhost:8000` and an empty `NEXT_PUBLIC_API_URL`, the app on port 3001 signed in and loaded a handover with every request going to port 3001 (`curl` and a browser run). A production build contains the rewrites and a build without `BACKEND_URL` contains none. Not tested: forwarding on Vercel to Render itself. A very long AI analysis could hit Vercel's own request time limit, which the local test cannot show. In that case use the direct mode.

## After deploying

Replace "TO ADD AFTER DEPLOYMENT" in the first row of `docs/ROUND2_SUBMISSION.md` with the live frontend address and the backend `/health` address. That row is the only place for the link. The README points to it.
